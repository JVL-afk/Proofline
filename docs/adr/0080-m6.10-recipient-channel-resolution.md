# ADR-0080: M6.10 recipient & channel resolution engine

- **Status:** Accepted — architecture and engine implemented; third-party
  source authorities remain `NOT_AUTHORIZED` pending separate legal review.
- **Date:** 2026-09-06
- **Decision owners:** PROJECT_OWNER (authorized "M6.10 RECIPIENT & CHANNEL
  RESOLUTION ENGINE")
- **Related:** ADR-0035 (fixture eligibility / A-17 live gate), ADR-0043,
  ADR-0049 (production separation of duties), ADR-0078/0079 (M6.9 Path B),
  `a17-attorney-result-2026-08-21.json` (person/contact enrichment as a
  mandatory legal re-review trigger)

## Context

The A-Plus M6.9 pilot correctly identified the preferred decision-maker
(Greg Yamin, President) but had no general, reusable mechanism for
discovering and verifying a contact endpoint for them — it hit a dead end at
"no email published on the company's own site" with no principled next
step. PROJECT_OWNER designated recipient and channel resolution a core,
general capability rather than an A-Plus-specific patch.

## Decision

Build `opintel_contact_resolution` (core) + `opintel_contact_resolution_local`
(persistence) implementing a deterministic, evidence-bound pipeline:

```
QUALIFIED_COMPANY -> OPPORTUNITY_CONTEXT -> ROLE_REQUIREMENTS ->
PERSON_DISCOVERY -> PERSON_IDENTITY_RECONCILIATION -> ROLE_RANKING ->
CHANNEL_DISCOVERY -> ENDPOINT_CANDIDATES -> SOURCE_RECONCILIATION ->
ENDPOINT_VERIFICATION -> LEGAL_POLICY_GATE -> SUPPRESSION/DNC ->
CHANNEL_RANKING -> RECIPIENT_AND_CHANNEL_PLAN
```

### Core truth invariant

`DISCOVERED != VERIFIED`, `PLAUSIBLE != TRUE`, `VERIFIED != LEGALLY_AUTHORIZED`,
`AUTHORIZED_CHANNEL != AUTHORIZED_SEND`, `UNKNOWN` stays `UNKNOWN`. Enforced
structurally: `EligibilityDisposition` is only ever produced by the
deterministic gate functions in `application.py`/`ranking.py`; no LLM call
exists anywhere in this package's decision path (an LLM may only, later,
help phrase an already-authorized message from an already-approved envelope
— section 20 of the authorization, not implemented as part of this
architecture since it belongs to the existing M6.8 communication layer).

### Authority boundary

M6.10 resolves and ranks; it never sends. Every `Channel`'s
`ChannelDeliveryMode` is fixed at `EXISTING_M6_M69_CONTROLS` (email),
`MANUAL_HUMAN_ONLY` (LinkedIn), or `HUMAN_CALL_ONLY` (phone) — SMS and
autonomous voice are `NOT_AUTHORIZED` and have no implementation at all,
not merely a disabled one.

### Source taxonomy and legal/source authority

11 `SourceCategory` values (first-party explicit/person-role/role-mailbox;
approved directory/profile/enrichment/verification; multi-source
corroborated; pattern-derived; search-discovery-only; unauthorized), kept
separate from provider identity (`SourceProviderPort.provider_name` is a
free string, never a business-logic branch). `SourceAuthorityMatrix` maps 6
`AuthorityDomain` values (third-party contact source, professional
directory, contact enrichment, email verification, LinkedIn profile
discovery, phone contact data) to `NOT_AUTHORIZED` / `AUTHORIZED_WITH_CONTROLS`
/ `AUTHORIZED`, defaulting fail-closed to `NOT_AUTHORIZED` for every domain
(`DEFAULT_AUTHORITY_MATRIX`). `source_category_authority_level` and
`require_authority` are the only functions that grant a category anything
beyond `CONTACT_SOURCE_NOT_AUTHORIZED` discovery-only status; first-party
categories are always `AUTHORIZED` (no third-party gate needed for a
company's own published pages).

### Email resolution and verification

7 `EmailKind` values; a `PATTERN_DERIVED_EMAIL` is rejected before any other
check (`evaluate_email_eligibility`) regardless of confidence, and can only
advance if policy explicitly sets `pattern_derived_email_permitted=True`
*and* the candidate is independently re-verified through an authorized
verification method's own authority — never through any authority of its
own (`PATTERN_DERIVED`/`SEARCH_DISCOVERY_ONLY` structurally carry no
authority mapping). 7-state `EmailVerificationState` with a strict monotonic
ranking (`verification_meets_threshold`); required thresholds are
per-`SourceCategory` configuration (`ContactSourcePolicySettings`), never
hard-coded to one provider. No SMTP probing is implemented.

### LinkedIn (manual-only) and phone (human-call-only)

LinkedIn discovery produces `LINKEDIN_PROFILE_VERIFIED` /
`_PROBABLE` / `_UNVERIFIED`; only `MANUAL_HUMAN_ONLY` delivery is ever
possible, and eligibility still requires `LINKEDIN_PROFILE_DISCOVERY_AUTHORITY`
to be granted. Phone distinguishes `MAIN_BUSINESS_PHONE` (no third-party
authority needed, first-party) from `DEPARTMENT_PHONE`/`DIRECT_BUSINESS_PHONE`
(need `PHONE_CONTACT_DATA_AUTHORITY`), and `PhoneReachability.INDIRECT` vs
`DIRECT` so a main line is never represented as reaching a specific person.

### Endpoint evidence record

`ContactEndpointEvidence` (frozen dataclass) is the section-12 authoritative
record: company/person id, role + evidence, channel + endpoint + kind,
source category + provider + URL, observed timestamp, source evidence
hash, identity/domain match booleans, verification method + result, source
conflicts, confidence, legal source authority, channel authority,
suppression status, retention classification, eligibility disposition, and
a content-addressed `evidence_record_hash`. Persisted append-only via
`SqlAlchemyContactEndpointEvidenceRepository` (SQLite/PostgreSQL, mirrors
the Stage A suppression-registry persistence pattern) — a corrected record
is a new row, never an edit.

### Eligibility state machine

13 `EligibilityDisposition` values; `BLOCKING_DISPOSITIONS` names every
disposition that must always fail closed. Providers/LLMs cannot override
any of them — there is no override parameter anywhere in this API surface.

### Privacy minimization

`minimize_raw_result` strips any raw provider field outside a fixed durable
allowlist (name/role/endpoint/channel/source/verification/eligibility)
before anything is persisted — EPHEMERAL_RAW_RESULT ->
DETERMINISTIC_CONTACT_MINIMIZATION -> DURABLE_MINIMIZED_CONTACT_EVIDENCE.

### Suppression / DNC integration

Extended `opintel_suppression.SuppressionKind` with `PERSON_SUPPRESSED`,
`CHANNEL_SUPPRESSED`, `COMPANY_SUPPRESSED` (additive; `ADDRESS_SUPPRESSED`/
`DOMAIN_SUPPRESSED` and every Stage A behavior unchanged) and added
`suppress_person`/`suppress_channel`/`suppress_company`/
`check_channel_blocked` to `SuppressionRegistryService`, reusing the same
append-only repository rather than building a parallel suppression system.
A channel-level opt-out never silently suppresses a different channel for
the same person unless a `PERSON_SUPPRESSED`/`COMPANY_SUPPRESSED` entry (or
a project-level `OPT_OUT_ALL_PROOFLINE_OUTREACH`-style policy, left as a
future configuration flag, not hard-coded) says so.

### Provider adapter architecture

`SourceProviderPort` (Protocol) + `NullSourceProvider` (the only
implementation in this codebase — always returns no results, makes no
network call). No RocketReach/ZoomInfo/Apollo/Hunter-specific code exists
anywhere in this package.

### Cost controls

`CostBudget`: max candidate people per company, max providers queried (0 in
this milestone), max queries per person, max paid cost, stop-once-eligible
flag — enforced by the caller (a future orchestrator/script), not
implicit.

## Consequences

- A-Plus's Greg Yamin resolution is now expressed generally: `EMAIL`
  blocked on `IDENTITY_VERIFIED_CONTACT_UNRESOLVED` (no endpoint exists),
  `LINKEDIN` blocked on `CONTACT_SOURCE_NOT_AUTHORIZED` (discovery
  authority not granted), `PHONE` eligible for a human-operated indirect
  call via the verified main business line.
- No third-party contact-enrichment call has been made, and none can be
  until PROJECT_OWNER supplies the separate legal/source authorization this
  ADR's counsel-decision companion document requests.
- This does not change M6.9 Path B, M6.8-3's `NOT_CERTIFIED` status, or the
  A-Plus pilot's paused-at-recipient-resolution state.

## Validation

`tests/test_m610_contact_resolution.py` — fixtures A-O (owner authorization
section 27) plus persistence/restart and hash-stability tests. Full suite
1237 passed, 3 skipped (pre-existing, Postgres-gated); ruff + mypy strict
clean.

## Revisit triggers

A third-party contact source, LinkedIn profile-page fetching, or direct
phone data is proposed for real use — each needs its own
`AuthorityDomain` grant plus the legal review its own precedent A-17 record
already flags as mandatory, not merely code deployment.
