# ADR-0075: Terraform Phase 1 provisioning and protected remote state

- **Status:** Accepted
- **Date:** 2026-08-21
- **Decision owners:** Project owner and architecture owner
- **Related architecture decisions:** A-03, A-04, A-07, A-08, A-18; ADR-0074
- **Supersedes:** None

## Context

M6.7 Phase 1 needs deterministic AWS provisioning before actual environment evidence can satisfy
A-03/A-04/A-07. No AWS account, credential, role assignment, legal approval, final retention policy,
or charge authorization currently exists. The repository therefore needs reviewable infrastructure
code without treating configuration as deployment evidence or authorizing a live operation.

Official sources reviewed on 2026-08-21 and the checksum-verified release binary identify Terraform
1.15.9 and the HashiCorp AWS provider 6.53.0.
HashiCorp's S3 backend supports `use_lockfile = true`, recommends bucket versioning, and marks
DynamoDB-based locking deprecated. Backend credentials or sensitive values must not be placed in
backend command arguments or committed configuration.

## Decision drivers

- Reproducible, reviewable AWS plans with exact provider identity.
- Encrypted, access-controlled, recoverable state with concurrency protection.
- No secret, legal conclusion, live authority, or deployed-evidence fabrication.
- Separate plan, apply, discovery, research, and slot-execution approvals.

## Considered options

1. Terraform CLI with an S3/KMS remote backend and S3 lockfile locking.
2. OpenTofu with an S3 backend.
3. AWS CloudFormation/CDK.
4. Console-only provisioning.

## Decision

Use HashiCorp Terraform CLI `>= 1.15.9, < 1.16.0` for the first Phase 1 environment. Pin
`hashicorp/aws` to exactly `6.53.0` and commit the dependency lock file generated by the approved
Terraform binary before plan approval. A provider upgrade requires a reviewed successor change and
new plan; a Terraform minor-version change requires ADR review.

Store each environment's state in its own dedicated, pre-created Amazon S3 backend object. Enable
bucket versioning, Block Public Access, TLS-only access, customer-managed KMS encryption, CloudTrail
data-event logging, least-privilege state-reader/writer roles, and `use_lockfile = true`. Do not use
deprecated DynamoDB locking for this new state. Backend bucket, key, region, KMS key, and role are
supplied through an owner-approved partial backend configuration file outside Git. Credentials use
short-lived OIDC/IAM Identity Center federation or workload identity and never backend arguments.

The Terraform state administration boundary is separate from the Phase 1 workload authority. For
the bounded 24-company pilot, the protected state resources and workload may reside in the same
dedicated AWS account; separate bootstrap, state-plan, state-apply, workload-plan, workload-apply,
operator, worker, and kill-switch roles preserve the boundary. A second AWS account is not required.
State read access is sensitive because state may expose resource metadata. Do not deliberately place
passwords, tokens, private key material, page content, personal/contact data, or provider credentials
in variables, outputs, provisioners, user data, or state. Prefer AWS-managed password generation,
IAM database authentication, and resource references.

Use separate accounts and state keys for each future environment. Phase 1 initially targets one
dedicated approved AWS workload account in `us-east-2`. The root module asserts the expected account
and region and defaults the worker to zero desired tasks; concurrency can never exceed one.

Planning and applying are distinct approval events:

1. `terraform init` uses the approved partial backend file.
2. `terraform validate`, formatting, security checks, and a saved binary plan run under a read/plan
   role.
3. The plan hash, provider lock hash, configuration hash, cost estimate, policy evidence, and exact
   target account are reviewed by the security/environment owner and project owner.
4. Apply requires an explicit, expiring apply approval and separately authorized short-lived apply
   role. Apply consumes only the reviewed saved plan.
5. Outputs are observed again through AWS control-plane evidence before A-03/A-04/A-07 approval.

Terraform apply never authorizes discovery, research, a worker run, person/contact processing, AI,
browser activity, or delivery. No infrastructure command is authorized until exact AWS charge
authorization, credentials, backend values, roles, final retention inputs, and environment approvals
exist.

## Consequences

### Positive

- Infrastructure intent, provider versions, state policy, and approvals are reviewable.
- State locking and versioning reduce concurrent-write and accidental-loss risk.
- Actual control-plane evidence remains distinct from desired configuration.

### Negative

- The state bootstrap and workload account must exist before the root module can initialize.
- Exact provider locking requires an authorized provider download before the first plan.
- Terraform state remains sensitive operational data even with secret-minimizing design.

### Risks and mitigations

- State disclosure: restrict object/KMS access, log access, encrypt, version, and audit regularly.
- Plan/apply drift: apply only the saved plan and invalidate approval on configuration/provider drift.
- Hidden spend: require the USD 250 ceiling, cost estimate, budget alarms, and explicit charge approval.
- Accidental live behavior: desired worker count defaults to zero and all live permissions remain
  independently `NOT_AUTHORIZED`.

## Validation

- CI checks formatting, validation, exact versions, forbidden provisioners/secrets, and no floating
  provider versions once Terraform is available.
- The provider lock file and saved-plan hash are mandatory before apply approval.
- Actual resource evidence and configuration hashes are required after apply.
- Application tests continue to prove discovery/research/slot authority separation.
