## The two coupled issues the probe exposed

### 1. Parser robustness bug — FIXED (within-scope)

`comm.stub_provider.parse_provider_response` — the function that turns a raw
provider response into `GenerationCandidate`s for the validator — **raised an
unhandled `ValueError`** when a claim-manifest entry carried
`asserted_strength: "REQUIRED_DISCLOSURE"`, a value outside our `FactStrength`
enum. The `try/except` only wrapped the top-level JSON load, not per-entry
parsing. A real, assumed-non-conformant provider **will** emit values outside our
vocabulary; a crash is never an acceptable handling of that.

Fixed: per-candidate parsing is now wrapped; a row that raises
`(ValueError, KeyError, TypeError)` — bad enum, missing field, wrong type — is
dropped and recorded, and a response with no surviving candidate returns
`GENERATION_REFUSED` with a reason. Non-list `candidates` handled. The stub
happy-path is byte-identical for well-formed input (M6.8-2 replay unaffected;
112 → 113 M6.8 tests pass). This does not change the manifest contract, the
validator, or any certification-key member.

### 2. The `@3` prompt does not specify the claim-manifest ENTRY schema — OWNER DECISION

Even with the parser hardened, the probe candidate is **dropped** (its manifest
entry is non-conformant) → 0 evaluable candidates → the run still cannot proceed.

Root cause: `@2` and `@3` ask for "a complete claim manifest mapping every
substantive clause ... to envelope 'ref' ids" but never state the **entry
schema** the deterministic validator expects. A real model, seeing a disclosure
clause and no vocabulary, reasonably invented `asserted_strength:
"REQUIRED_DISCLOSURE"`.

The schema the validator and `comm.stub_provider` require for each entry:

| field | value |
|---|---|
| `claim_id` | string |
| `claim_type` | one of `FACT`, `INFERENCE`, `RECOMMENDATION`, `QUESTION`, `DISCLOSURE`, `TRANSITION`, `SALUTATION`, `CTA`, `SIGNATURE_SLOT`, `NON_SUBSTANTIVE` |
| `rendered_artifact` | `"subject"` or `"first_contact_email"` |
| `rendered_span` | the exact substring of the rendered text |
| `licensed_source_ids` | list of envelope `ref` ids (may be empty for non-substantive spans) |
| `qualifiers` | list of strings (optional) |
| `asserted_strength` | one of `OBSERVED_PUBLIC_TEXT`, `OBSERVED_AVAILABILITY_SIGNAL`, `PUBLISHED_SELF_CLAIM`, `LICENSED_INFERENCE`, `LICENSED_RECOMMENDATION`, `VERIFIED_FACT`, or `null` |
| `cta_intent` | string or `null` |

Specifying this in the prompt is **not slimming or weakening** the manifest — it
is the opposite: making the full, existing contract legible to the provider so it
can produce a conformant manifest that the unchanged validator can evaluate.

## Options (owner decision)

1. **Authorize a `@5` prompt template** that states the claim-manifest entry
   schema above verbatim (fields + the two closed vocabularies). Everything else —
   the full manifest requirement, the validator, the frozen corpus, the
   thresholds, the 8000 ceiling, N=1, thinking disabled — unchanged. New
   certification key. Re-run the one authorized probe, then the 81. This is the
   minimal change that makes the accepted protocol actually completable.
   **Recommended.**
2. Keep `@3` and accept that a fraction of manifests will be non-conformant and
   dropped → the run will almost certainly fail the 0.80 pass-rate floor for a
   non-safety reason. Not useful.
3. Have the harness normalise obvious synonyms (`REQUIRED_DISCLOSURE` → the
   disclosure semantics) before validation. This is the harness interpreting the
   provider-declared manifest — arguably an alteration of what is being observed;
   not recommended.
