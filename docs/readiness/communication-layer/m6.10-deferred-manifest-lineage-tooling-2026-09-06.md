# Deferred tooling issue — reconstructed-manifest `no_company_specific_evidence` advisory

Owner authorization "ADDRESS PRIMARY_A PRE-APPROVAL FINDINGS", section 6.

## Status

**Deferred tooling / lineage work. NOT a launch blocker** (the existing policy
does not make it one: the finding is `ADVISORY` under validator contract v3 and
`OutputValidator(contract="v3").validate(...)` returns `passed = True`).

Do **not** weaken the validator, and do **not** alter the communication to make
this advisory disappear — both are explicitly forbidden by the authorization.

## What the advisory is

When the final recipient-bound package is assembled
(`scripts/run_m610_aplus_primary_a_package.py`), the frozen email body is
re-wrapped as a `GenerationCandidate` with an **empty `ClaimManifest`**
(`ClaimManifest(entries=())`) purely so the deterministic validator can be
re-run on the exact bytes that will be sent. The M6.9 Stage B run and the
M6.10 readability-revision run do not persist the provider's original
claim-manifest into the artifact JSON, so it cannot be reattached here.

With no manifest to corroborate, the validator's personalization-quality
heuristic cannot *positively confirm* a company-specific span and emits
`no_company_specific_evidence` as an ADVISORY note.

## Why it is a false signal here

The exact package body **does** contain company-specific licensed evidence,
verbatim from the frozen `real_aplus_envelope` (A-Plus's own public pages):

- `"The Austin Commercial AC Repair Company"` — A-Plus's commercial-HVAC
  self-description (`content_sha256 38abd278…`);
- `"When to Schedule AC Replacement"` — A-Plus's published guidance page
  (`content_sha256 7a9934dc…`).

Independent confirmation from the same validation run: canonical
reconciliation coverage `1.0`, `0` unresolved substantive claims, and the
quality assessor reports `uses_company_specific_evidence = True` /
`uses_strongest_hook = True`.

## The deferred fix (future work, needs its own bounded task)

Persist the provider claim-manifest (or the reconciled canonical claim map)
alongside `body_frozen` in the Stage B / revision artifacts, and have the
package builder reattach it before the final `validate(...)` call. Then the
advisory resolves on real evidence instead of being suppressed. This is
lineage/persistence plumbing — it changes no truth, no threshold, and no
validator rule.
