# M6.10 legal / source-authorization decision artifact — for Texas counsel

Prepared per owner authorization "M6.10 RECIPIENT & CHANNEL RESOLUTION
ENGINE", section 23. **This is a description of a proposed system for
counsel's review, not a legal opinion, and not an assumption of counsel's
answer.** Every decision field below is currently unanswered
(`NOT_APPROVED` is the fail-closed default this project's code already
enforces — `SourceAuthorityMatrix` defaults every authority to
`NOT_AUTHORIZED` — this document does not change that).

## 1. Purpose

Identify the correct business decision-maker(s) at a qualified opportunity
company and discover/verify a professional contact channel for them, so a
single, already-legally-reviewed first-contact message (governed separately
by the existing M6.8/M6.9 process) can reach the right person. This is not
a request to approve sending anything — sending remains gated by the
existing M6/M6.9 approval path regardless of what this document approves.

## 2. Data scope

**Professional/business data only.** Fields collected, when a source is
authorized: professional name, business/company, business role/title,
professional contact endpoint (business email, business phone, or a
professional-profile URL), source/provenance, verification result,
eligibility state. Explicitly **not** collected or durably retained even
when a source returns it: personal email, home address, personal phone,
birth date, family relationships, personal social content, consumer data,
sensitive personal data, or any other unrelated profile attribute
(`opintel_contact_resolution.minimize_raw_result` enforces this in code).

## 3. Proposed source categories (see ADR-0080 for the full taxonomy)

- First-party company pages (already in scope; no separate authorization
  needed — this is the company's own published information).
- Approved professional directories (e.g. a business-directory service).
- Approved professional-profile discovery (e.g. LinkedIn, via public search
  results — not authenticated/gated scraping).
- Approved contact-enrichment services (e.g. RocketReach, ZoomInfo, Apollo,
  Hunter — no specific provider is pre-selected; this document asks counsel
  to approve the *category*, with a specific provider named separately once
  counsel's category-level answer is known).
- Approved email-verification services.

**No provider in the above categories has been queried by this project.**

## 4. Minimization, provenance, retention

Every retained field traces to an explicit source URL/reference (where
policy permits recording one), an observed/fetched timestamp, and — where
feasible — a source-content hash. Retention is per-`SourceCategory`
configuration (`ContactSourcePolicySettings.retention_period_days`), not a
single global rule; nothing is retained indefinitely by default; nothing
outside the minimization allowlist in section 2 is retained at all.

## 5. Suppression / do-not-contact

Integrated with the existing Stage A suppression registry
(`opintel_suppression`), extended with person-level, channel-level, and
company-level do-not-contact, in addition to the existing address/domain
suppression. No recommendation this system produces can bypass suppression.

## 6. Email verification

Supported verification states range from `SYNTAX_ONLY` through
`MULTI_SOURCE_VERIFIED`; no specific verification provider is hard-coded.
No SMTP mailbox-probing is implemented or proposed without separate,
explicit authorization.

## 7. LinkedIn / professional-profile use

Discovery and confidence-scoring only in this milestone. No automatic
connection request, no automatic message, no authenticated/gated scraping.
Any eventual message is a manually-composed, separately-reviewed human
action (same review standard as the existing M6.9 email pilot) — this
system only identifies and ranks the channel as a candidate.

## 8. Business phone resolution

Main business line and (if separately authorized) direct/department lines.
A main line is never represented as a specific person's direct number
(`PhoneReachability.INDIRECT` vs `DIRECT` is preserved through to any
report a human reviewer sees). No autonomous or AI-driven calling is
implemented or proposed. No call recording. No SMS.

## 9. Pattern-derived candidates

A pattern-generated email address (e.g. `first.last@domain`) is never, by
itself, treated as a usable contact under this system's code (enforced:
`PATTERN_ONLY_NOT_ELIGIBLE`). It may only advance to eligible if (a) policy
explicitly permits pattern-derived candidates for a given context and (b)
an independent, separately-authorized verification method confirms it —
never on pattern plausibility alone.

## 10. Decision fields for counsel

| decision | counsel's answer |
|---|---|
| `PROFESSIONAL_DIRECTORY_USE` | ☐ APPROVED ☐ APPROVED_WITH_CONTROLS ☐ NOT_APPROVED |
| `CONTACT_ENRICHMENT_USE` | ☐ APPROVED ☐ APPROVED_WITH_CONTROLS ☐ NOT_APPROVED |
| `EMAIL_VERIFICATION_USE` | ☐ APPROVED ☐ APPROVED_WITH_CONTROLS ☐ NOT_APPROVED |
| `PATTERN_DERIVED_BUT_INDEPENDENTLY_VERIFIED_EMAIL_USE` | ☐ APPROVED ☐ APPROVED_WITH_CONTROLS ☐ NOT_APPROVED |
| `PROFESSIONAL_PROFILE_USE` | ☐ APPROVED ☐ APPROVED_WITH_CONTROLS ☐ NOT_APPROVED |
| `BUSINESS_PHONE_RESOLUTION` | ☐ APPROVED ☐ APPROVED_WITH_CONTROLS ☐ NOT_APPROVED |
| `DIRECT_BUSINESS_PHONE_RESOLUTION` | ☐ APPROVED ☐ APPROVED_WITH_CONTROLS ☐ NOT_APPROVED |
| `RETENTION_CONTROLS` | ☐ APPROVED ☐ APPROVED_WITH_CONTROLS ☐ NOT_APPROVED |

None of these fields has been filled in by this task. This document does
not assume, infer, or pre-select an answer for counsel. Once returned, the
answers map directly onto `opintel_contact_resolution.domain.AuthorityDomain`
grants in code — no code change is needed to activate an approved source,
only a configuration change to the `SourceAuthorityMatrix` used for a run.
