## Options (owner decision — each changes a certification-key member or ceiling)

1. **N = 1 candidate per call.** Request one candidate per response; to keep the
   "3 candidates per envelope" intent, make 3 calls per repeat →
   9 envelopes × 3 repeats × 3 candidates = **81 calls** (still the §7 "81 max
   candidate outputs"). Fits in 2000 tokens comfortably. Changes the call/candidate
   structure and the prompt template (a certification-key member) — needs owner
   authorization. USD ≈ 81 × (~5,545 in @ $2 + ~1,200 out @ $10) / 1e6 ≈ **USD 1.87**.
2. **Lift the `max_output_tokens` ceiling** (e.g. to 8,000) so N = 3 + manifests
   fit in one response. Directly contradicts the §7 hard ceiling of 2,000 — owner
   would have to lift it. Smallest structural change; ≈ USD 1.5–2.5 for 27 calls.
3. **Slim the response contract** — drop or shrink the per-candidate claim
   manifest in the certification prompt, reconstruct manifests deterministically
   after the fact. Changes the prompt template and arguably the certification
   semantics. Keeps N = 3 and 2,000 tokens.
4. **Accept `NOT_CERTIFIED`** for M6.8-3 as configured and rethink the whole
   provider-generation approach.

Recommendation: **option 1** (N = 1 per call, 81 calls). It respects the 2,000
token ceiling as written, keeps the validator and corpus untouched, and the
81-candidate figure is already the authorized maximum. The prompt template gains
an `@3` variant that asks for exactly one candidate; new certification key.
