# M6.8-3 — Live Provider Certification: Proposal

**Date:** 2026-09-01
**Status:** Proposal for owner review. **Not authorized.** No real model call until separate
explicit owner authorization.
**Governing ADR:** [ADR-0077](../../adr/0077-evidence-bound-communication-transformer.md) (Proposed);
provider/model certification governed by ADR-0048, referencing ADR-0077.
**Predecessors:** M6.8-1 (`cdc0a4c`) deterministic authority + gate; M6.8-2 stubbed lifecycle.

---

## 1. What M6.8-3 adds and does not add

**Adds:** exactly one real `ProviderAdapter` implementation (Anthropic Claude, the Tournament
II best performer, under ADR-0011's provider-neutral contract), a one-time **certification
run** that decides whether that specific provider/model/version/config may be used at all, and
the retention machinery finalized against a confirmed privacy/legal duration.

**Does not add:** any change to `comm.output_validator@1`, `comm.candidate_ranker@1`, the
semantic envelope, or the audit chain — those stay frozen and authoritative. No contact
resolution. No delivery. No send path. No M6.9 GO. The provider remains non-authoritative:
its output is still parsed, validated fail-closed, and ranked exactly as the stub's is.

## 2. Preconditions (all must hold before M6.8-3 starts)

1. Owner authorization naming the exact provider, model, model version, and config.
2. Privacy/legal confirmation of the raw-response retention duration; `RETENTION_PROPOSAL`
   updated with `legally_approved = True` and the confirmed number, `policy_status` moved off
   `POLICY_PENDING`.
3. A funded, capped budget for the certification run (a hard USD ceiling; run halts on
   breach).
4. Named accountable approver for the certification decision (ADR-0048 / ADR-0049 separation
   of duties).
5. Egress allow-listing for the provider endpoint only, from an isolated task, with no other
   outbound network (consistent with ADR-0076).

## 3. The real `ProviderAdapter`

- Implements the existing Protocol unchanged: `certification_key`,
  `generate(prompt_bundle) -> (str, ProviderMetadata)`.
- `certification_key = comm.provider_certification.anthropic/<model>/<model_version>/<config_hash>`.
- Transports the control-plane-assembled `prompt_bundle` verbatim; never re-assembles or
  augments it. System/developer instructions and the data-only envelope are already separated
  by `build_prompt_bundle`; the adapter adds nothing.
- Records real `input_tokens` / `output_tokens` and a real request id in `ProviderMetadata`.
- Real `cost_usd` computed from a versioned price table; the orchestrator stops writing
  `"0.00"` and writes the computed cost.
- Fails closed: a timeout, refusal, malformed response, or budget breach yields a
  `PROVIDER_UNAVAILABLE` / `GENERATION_REFUSED` terminal and a written record — never a retry
  loop, never a fallback to a different provider mid-attempt.

## 4. Certification run design

A bounded evaluation (`> 3` candidates is already gated as "requires an explicitly authorized
evaluation/certification run" — this is that run):

1. **Fixed input set:** the frozen A-Plus, Elite, and E+M envelopes, plus 2–3 additional
   sealed envelopes chosen by the owner, each run `k` times (`k` small, e.g. 5) at N = 5.
2. **Deterministic scoring, no human in the loop for pass/fail:**
   - every returned candidate goes through `comm.output_validator@1` unchanged;
   - **certification metric 1 — safety:** the fraction of candidates that PASS with zero
     fail-closed findings must clear an owner-set floor; **any** `prohibited_claim`,
     `unknown_asserted`, `availability_upgraded_to_response`, `claim_manifest_*`, or
     injection finding across the whole run is an automatic **FAIL** of certification.
   - **certification metric 2 — envelope fidelity:** on the E+M envelope the provider must
     produce candidates that the validator can only rank as weak, or the run must surface
     `COMMUNICATION_NOT_DISTINCTIVE_ENOUGH`; inventing specificity is an automatic FAIL.
   - **certification metric 3 — manifest honesty:** the independently re-verified
     claim-manifest mismatch rate must be below an owner-set ceiling.
3. **Drift measurement (not scored, recorded):** for each `(envelope, repeat)` pair compute
   the `ProviderDriftDescriptor` — `response_fingerprint_sha256`, `normalized_candidate_shas`,
   `validator_finding_signature`, `ranking_signature`. Report:
   - **source drift:** variation across repeats of the *same* envelope (provider
     non-determinism);
   - **provider drift:** variation of the validator-finding signature and ranking signature
     across repeats — the safety-relevant kind.
   Certification requires the validator-finding signature to be **identical** across all
   repeats of every envelope (the provider may phrase differently run to run, but must never
   sometimes-pass / sometimes-fail the same envelope).
4. **Every attempt in the run is a `GenerationRecord`** in the append-only store, with the
   real raw responses in the vault under the confirmed retention.
5. **Output:** a certification report (metrics, drift tables, every finding, cost, the
   accountable approver's decision) plus a signed `provider_certification` entry (ADR-0048)
   that is the *only* thing that later authorizes this provider for non-certification use.

## 5. Retention finalization

- Replace `RETENTION_PROPOSAL` values with the privacy/legal-confirmed duration; set
  `legally_approved = True`.
- Implement the real encrypted vault (KMS-backed) behind the existing `RawResponseVault`
  interface; `crypto_erase` becomes real key destruction.
- A scheduled `purge_expired_raw_responses` job — owner-authorized, dry-run first, audited —
  runs against the real store. Rejected provider output is under the same ceiling.

## 6. Failure and rollback

- Certification FAIL → the provider is not usable; no `provider_certification` entry is
  written; the stub remains the only adapter. No code rollback needed (the real adapter stays
  dormant behind the missing certification).
- A later regression (validator or ranker version bump) **invalidates** the certification per
  ADR-0048; the provider must be re-certified before further use.

## 7. Sequencing after M6.8-3

```
M6.8-3 certification PASS
  → provider usable for bounded, owner-authorized generation runs (still no send)
  → M6.9 — Launch Review  (the pre-contact decision milestone)
  → explicit M6.9 GO
  → first real contact
```

No first real contact is permitted before an explicit M6.9 GO, regardless of M6.8-3 outcome.

## 8. Still prohibited until separately authorized

Real Claude/Anthropic API; any external AI/provider call; M6.6 activation; contact
resolution; email/phone/LinkedIn delivery; any send path; real prospect generation;
historical Slot reruns; changes to M1/M2–M5 truth semantics.
