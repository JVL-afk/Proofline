## 2. Suppression registry design

- `SuppressionKind`: `ADDRESS_SUPPRESSED`, `DOMAIN_SUPPRESSED`.
- `SuppressionEntry` (frozen dataclass): normalized email/domain, scope, reason,
  source mechanism, opt-out-received timestamp, suppression-effective
  timestamp, evidence/provenance reference, `audit_event_hash` (sha256 over a
  canonical JSON of every fact needed to prove the suppression), created-at.
- Deterministic: `normalize_email`/`normalize_domain` are pure functions;
  `SuppressionRegistryService.check_eligibility` has no randomness, no network
  call, and no parameter that changes its answer other than the registry
  state itself.
- Provider/LLM cannot override it: nothing in `opintel_communication` or
  `opintel_outreach` consults an LLM to decide eligibility; eligibility is
  computed only from repository state.
- Checked before every send-eligibility decision via
  `enforce_pre_send_suppression_gate`, which has no override/bypass
  parameter of any kind.
- Applies immediately: `record_address_opt_out`/`suppress_domain` persist
  synchronously before returning; the very next `check_eligibility` call
  sees the new entry.
- No automatic unsuppression: there is no TTL, no cron, no expiry field on a
  `SuppressionEntry`. The only way to lift a suppression is
  `owner_authorized_unsuppress`, which requires a non-empty `authorized_by`
  and `reason` and appends a separate `OwnerUnsuppressionRecord` (append-only;
  the original entry is never edited or deleted).

## 3. Opt-out workflow

Reply-based, for this pilot. Default copy (`render_opt_out_notice`, company
name configurable):

> To stop receiving email from Proofline, reply to this message with the word
> UNSUBSCRIBE. We will remove your address within three days.

No unsubscribe URL — the only externally permitted URL in this pilot is the
separately-authorized demo URL (ADR-0079), and it is not conflated with the
opt-out mechanism.

Operator workflow (`ingest_operator_observed_opt_out`, manual ingestion,
pilot-appropriate — no mailbox automation was built or is needed for one
recipient):

`recipient replies UNSUBSCRIBE to andrew@proofline.business (monitored)` ->
`operator observes the reply` -> `operator calls ingest_operator_observed_opt_out`
-> `suppression registry updates (effective = min(received_at, recorded_at))`
-> `future check_eligibility calls fail for that address`.

Records `received_at`, `suppressed_at`, `elapsed`, and `within_sla` (bound:
`OPT_OUT_SUPPRESSION_MAX_SLA = timedelta(days=3)`) for every ingestion.

## 4. Persistence model

`SqlAlchemySuppressionRepository`: two SQLite/PostgreSQL tables,
`suppression_entries` (append-only, unique on
`workspace_id, kind, normalized_value`) and
`suppression_owner_unsuppressions` (append-only, references an entry by id).
`get_active_entry` returns `None` if a matching entry has a later
unsuppression record — eligibility is derived from the append-only log at
read time, never from a mutated "active" flag. Verified to survive a fresh
`SqlAlchemySuppressionRepository` instance against the same database file
(process-restart simulation).

## 5. Pre-send enforcement

`enforce_pre_send_suppression_gate(service, workspace_id=..., candidate_email=...)`
re-checks eligibility at the moment of the call — never from a cached
decision — and raises `DeliveryBlockedSuppressed` if blocked. A package
approved before a recipient opts out is therefore invalidated the next time
this gate runs, with no code path to skip it.
