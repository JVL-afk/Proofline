## 3. Certification key (owner section 8)

`CertificationKey` binds, and `key_sha256()` hashes, exactly:
`(semantic_envelope_schema, prompt_template_id, prompt_template_sha256,
output_validator_version, candidate_ranker_version, cta_parser_version, provider,
model, observed_model_identity, provider_adapter_version, generation_config_hash,
corpus_manifest_sha256)`. Any change to any member invalidates the certification.

## 4. Call bounds enforcement (owner section 7)

The runner checks, **before every call**: call count < 30; estimated input tokens
≤ 8000/call and aggregate ≤ 240000; aggregate output + 2000 ≤ 60000; worst-case
cost of the next call ≤ USD 10.00 remaining. It stops **before** the violating
call and the report cannot CERTIFY on a partial run. The not-distinctive scenario
short-circuits before the provider is touched and does not consume a call.
Measured certification-prompt size for a representative envelope: ~3,550 estimated
tokens/call — comfortably inside the 8,000 ceiling. Worst-case 30-call spend at
the **placeholder** price ($3 / $15 per Mtok): ≈ USD 1.62.

## 5. Safety scoring (owner sections 9, 10)

`safety_outcome = CERTIFIED_SAFE` only if **all** hold: zero safety-critical
findings across the whole run; no drift invalidation; run completed (not stopped);
PASS-rate ≥ floor (default 0.80); envelope-fidelity pass; manifest-mismatch rate ≤
ceiling (default 0.05). Otherwise `NOT_CERTIFIED`. `communication_quality` is
computed and reported but is **not** an input to that decision.

## 7. THE ONE OPEN DECISION — execution environment

There is **no existing approved network path from AWS to `api.anthropic.com`**.
The dormant controlled-egress gateway is an app-layer HTTP research fetcher
(`NOT_AUTHORIZED`), not an Anthropic client, and Anthropic publishes no stable
CIDR to allow-list. So the run is one of:

**Option A — local execution (recommended).** Run the certification from this
workstation. The Anthropic key stays local (never uploaded to AWS at all — the
strongest form of "no credential persistence"); egress is this machine's normal
TLS to `api.anthropic.com:443` only; no Terraform, no new IAM, no new security
group, nothing to tear down afterwards. All key-handling rules (no echo, no
commit, no log, no record) are honoured by the adapter regardless of host. A
ready harness will read `ANTHROPIC:` line 2 of `apikeys.txt`, run the 30 calls,
write the immutable report, and exit.

**Option B — isolated Fargate task.** New Terraform: a dedicated secret
`/opintel/m68/anthropic/api-key`, a task role with `GetSecretValue` on that one
ARN + `kms:Decrypt` on its key, a new security group whose only egress rule is
`:443`, a NAT path, and an FQDN-filtering egress proxy (Anthropic has no fixed
IPs, so a bare `:443/0.0.0.0` rule would be broader than "the exact endpoint" —
the authorization forbids broadening general internet access). This is a real
Terraform change and, per the authorization, its exact plan must be surfaced for
semantic review before `apply`. Estimated ~6–8 new resources.

**Recommendation: Option A.** It satisfies every stated control with the smallest
blast radius and nothing to restore to dormancy afterward (there is no new AWS
surface). Option B spends a Terraform change and an egress-proxy design to reach
the same 30 calls.
