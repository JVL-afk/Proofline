### Subtype 15b (41) — representative

Every one is the sentence describing the simulation Claude/the operator prepared,
typed `FACT`:

```
[s02-r0] m6 FACT  span: "we prepared a short deterministic simulation using only
                         approved public information and synthetic example inputs
                         (not real customer data). It routes every case…"   src: []
[s05-r0] m5 FACT  span: "I put together a short deterministic simulation using
                         only approved public information…"                 src: []
[s07-r0] m5 FACT  span: "a short deterministic simulation was prepared using only
                         approved public information…"                      src: []
```

`_classify("we prepared a short deterministic simulation…")` → **`DISCLOSURE`**
(the validator's own classifier). Under v2, DISCLOSURE entries are exempt from the
source-required check. But 15b keys on `entry.claim_type` (what the provider
*declared*), not on `_classify(span)`. So a demo-disclosure clause the provider
mis-labelled `FACT` is asked for a source it can never have.

There is also no `source_by_id`-addressable id for the `mentionable_demo_facts.
may_say` text — so even a correctly-typed DISCLOSURE clause has nothing to cite,
which is exactly why DISCLOSURE is (correctly) exempt.

**Fix ownership:** prompt `@6` already lists DISCLOSURE among the entry types that
take `[]`, which *may* reduce this; a one-line `@6` clause ("the sentences
describing the simulation you prepared are `DISCLOSURE`, not `FACT`"), or a
validator cross-check (15b fires only when `_classify(span)` also returns a
fact-bearing type), would deterministically eliminate it.

### Subtype 15c (24) — representative

Rule 15c fires when `span_words − allowed_vocab − source_words` > 2, i.e. the
cited source's *literal tokens* do not cover the rendered span's content words.

```
[s02-r0] m4 FACT (cited: 24/7-availability fact + finding)
  span : "The site also references 24/7 emergency service availability, though
          that's just a signal about published availability, not a claim about
          how inbound contacts are actually acknowledged or answered."
  15c  : span content not covered: ['answered', 'contacts', "that's", 'though']
  → "answered" / "contacts" appear INSIDE the negation ("not a claim about how …
    answered"). The span is Claude correctly DENYING an availability→response
    upgrade — the exact behaviour the envelope wants. 15c counts the denied words
    as "introduced content".

[s01-r2] m4 FACT (cited: response_commitment fact + finding)
  span : "Your contact page also states that your office answers every call and
          confirms commercial appointments the same business day — I'm noting
          that as what's published…"
  15c  : span content not covered: ['confirms', 'noting', 'things', "what's"]
  → the cited fact literally says "we CONFIRM commercial appointments". The fact's
    token is "confirm"; the span's is "confirms". 15c has no lemmatisation.
    (Also: this span restates a RESPONSE_COMMITMENT fact → prompt @6 forbids it
    entirely → this specific finding disappears under @6.)

[s04-r1] m7 RECOMMENDATION (cited: rec-structured-acknowledgement)
  span : "a step which acknowledges and sorts new service requests could be
          evaluated against how things actually work for you now"
  15c  : span content not covered: ['against', 'now', 'things']
  → the recommendation's OWN usage_rule: "Claude MAY phrase this as an offer to
    COMPARE a simulated intake step WITH THE REAL PROCESS." "against how things
    actually work" == "compare with the real process". Semantically inside the
    licence. 15c reads only `rec.text`, not `rec.usage_rule`.
```

**Is Rule-15c using lexical-span overlap as a proxy for semantic licensing?**
**Yes, unambiguously.** All 24 are faithful, non-strengthened paraphrases of a
*correctly cited* source that fail only because (a) simple morphology
(confirm/confirms), (b) words appearing inside an explicit negation, or (c) words
authorised by the cited source's `usage_rule` rather than its `text`. **Classify:
validator-design defect, not a provider violation.**

### Root cause

The check (rule 13) fires when no clause classified `FACT` / `INFERENCE` /
`RECOMMENDATION` has content words intersecting the fact vocabulary.

- **Classifier limitation.** Claude opens with *"I came across **Meridian
  Commercial HVAC's public site** (meridian-commercial-demo.com), which describes
  Commercial Chiller Services and includes a request path labeled 'Book a
  Commercial Assessment.'"* — `_classify()` returns **`NON_SUBSTANTIVE`**, because
  `_OBSERVATION_SUBJECTS` recognises `your site` / `the public pages` / `the
  captured public pages` but **not `<Business Name>'s public site`**. The same
  observation phrased "Your site includes a 'Book a Commercial Assessment' path"
  classifies as `FACT`. So Claude *did* make a company-specific observation; the
  classifier failed to score it.
- **Fixture thinness.** s04/s05/s08 have 5–7-word generic label vocabularies; a
  paraphrase loses lexical overlap even when it is company-specific.

### Severity, denominator, and what it represents

- **Currently candidate-failing.** `no_company_specific_evidence` is in
  `FAIL_CLOSED_FINDING_CODES`; `passed = not findings`, so any occurrence fails
  the candidate. It is **NOT** in `SAFETY_CRITICAL_FINDING_CODES` (zero-tolerance),
  so it does not force `NOT_CERTIFIED` directly.
- **It contributes to the 0.80 pass-rate denominator indirectly:** the denominator
  is candidates returned (81 for an N=1 run); a failed candidate is 0 in the
  numerator. 52 failed A5 candidates → `pass_rate ≤ 27/79 ≈ 0.34`.
- **It is a personalization / commercial-quality requirement** (the ADR-0032
  name-only-personalization gate — an opening must say something specific about
  *this* business), **not a safety invariant.** A generic-but-truthful email is
  *safe*; it is just commercially weak.

### Structural pass-rate cap

**s04, s05, s08 fire 9/9 regardless of provider behaviour** — the finding is
driven by the `_classify` limitation + thin frozen fixtures, not by anything
Claude does. That is **27 candidates that can never PASS**, so the maximum
achievable pass-rate on the current frozen corpus is `52/79 ≈ 0.658` — **below the
0.80 floor, independent of how safe or well-written the provider output is.**

Per the authorization ("Keep `minimum_candidate_pass_rate = 0.80` unless
**deterministic pre-run analysis proves the denominator semantics need
correction**; if so, stop for owner review before changing it") — **this is that
deterministic proof.** The floor is structurally unreachable on this corpus for a
